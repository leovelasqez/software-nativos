# API de fundamentos v1 — Incremento 1

Normativa de payloads: `contracts/foundation-api-v1.json` desde raíz. JSON cerrado: campos desconocidos rechazados (400), nunca ignorar silenciosamente rol/costo enviado. HTTP JSON, body máximo 32 KiB, Cache-Control no-store en API. Error `{code,message}` sin SQL, credenciales ni stack. 400 validación, 401 sesión ausente/expirada, 403 permiso/origen, 404 registro inexistente en ámbito, 409 conflicto, 429 límite temporal, 500 fallo interno genérico.

Bootstrap: GET /api/status entrega setupRequired. POST /api/setup crea primer dueño con nombre/login/contraseña elegidos; sesión nueva. Lock transaccional evita carrera. Semillas organizativas no incluyen usuarios. Login case-insensitive, error genérico; límite por IP (10 intentos/minuto) y bloqueo temporal persistido por login tras fallos (5/15 minutos). Reiniciar proceso no elude bloqueo de cuenta. Sesión 12 horas, cookie nativos_session, hash guardado, browser deviceId generado por servidor (no identidad física de caja). Cambios de usuario invalidan todas sus sesiones. Logout elimina sesión y cookie. GET /api/me solo devuelve usuario público, acciones efectivas, sucursales visibles y deviceId de sesión.

X-Nativos-Request: 1 obligatorio en POST/PATCH/DELETE; Origin validado contra origen configurado si está presente. Solo mismo origen, sin CORS, host loopback configurado. No activar en LAN ni producción. Transporte HTTPS/cookie Secure y operación central requieren preparación posterior.

GET /api/branches filtra sucursales asignadas; GET /api/branches/{id} aplica authorize data.read y devuelve bodegas/equipos de ese local. Los recursos de caja registrados aquí no habilitan cobros ni autenticación offline.

Dueño con settings.manage administra usuarios y organización. Usuarios visibles solo si todas sus sucursales pertenecen al alcance del administrador. Crear/editar exige branchIds existentes dentro de ese alcance. Al cambiar nombre/login/rol/permisos/estado/contraseña se conserva identidad y se invalidan sesiones. No desactivar ni degradar el último dueño activo con settings.manage. No eliminar usuarios. Permisos iniciales por rol; formulario permite configurar acciones sin conceder cost.* o loyalty.adjust a no dueños. Motivo obligatorio, salvo configuración inicial (motivo fijo de inicialización).

POST /api/branches crea sucursal, bodega de venta y caja, y concede nuevo local al creador en misma transacción. PATCH /api/branches/{id} renombra con motivo. POST/PATCH warehouses permite agregar/renombrar y cambiar bodega predeterminada atómicamente. POST/PATCH devices permite registrar/renombrar/activar/desactivar equipo y modelo de impresora; solo una caja activa por sucursal. Modelos iniciales se preservan; nuevos modelos provienen de entrada explícita, no inferencia. Dispositivos desactivados no se borran. Reasignación entre sucursales no expuesta.

Auditoría: identificador único, actorId/kind, deviceId de sesión, branchId (null para evento global de identidad), operación, acción, occurredAt/receivedAt en servidor, motivo y cambios públicos antes/después. Sin password/hash/session token. Evento bootstrap usa deviceId generado. Login/logout auditados. Los eventos globales de identidad solo son visibles para dueños cuyo alcance incluye todos los locales del sujeto; además se conservan scopeBranchIds del evento para no filtrar historia al cambiar la asignación. GET /api/audit?branchId=&before=&limit= admite 1..100 y cursor id numérico descendente; devuelve items/nextCursor. Sin endpoint de modificación ni eliminación.

Listas de usuarios/sucursales pequeñas se devuelven completas dentro de alcance. Auditoría paginada mediante id para evitar duplicar/saltar entradas ante nuevas escrituras. Campos sensibles jamás se seleccionan para respuestas. Permisos comerciales AC-001-02/03 se integran en módulos posteriores, no se simulan aquí.

Mutaciones son atómicas con auditoría. Alta repetida de login/nombre sucursal devuelve conflicto por unicidad; no se ofrece reintento automático de POST en frontend. La idempotencia comercial general se mantiene pendiente del incremento 3. Conflictos de última caja/bodega/administrador se serializan en BD.
